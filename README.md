# 햄버거 프랜차이즈 주문·관리 시스템

소프트웨어공학 3조의 설계에 따라 만든 키오스크와 매장 관리 프로그램입니다. 고객은 판매 가능한 버거와 옵션을 선택해 결제하고, 관리자는 같은 데이터베이스에서 가격·품절 여부와 조리 상태를 관리합니다.

## v1.9 — 본사에서 가맹점 개설·점주 초대

본사 계정으로 로그인하면 **본사 관리**가 먼저 열립니다. **가맹점 개설 · 점주 초대**에서 가맹점 이름, 점주 이메일, 기본 구성을 가져올 매장을 선택하고 **기본 구성으로 개설하고 점주 초대**를 누릅니다. 기존 매장(매장 1)을 기준으로 선택하면 현재 준비된 구성을 그대로 출발점으로 사용할 수 있습니다.

- 새 매장에 메뉴 이름·설명·정상가·사진·활성 추가 옵션·세부 선택 그룹·분류·메뉴 순서·광고를 복사합니다. 메뉴·옵션 ID는 새로 부여하고 사진은 변경 불가능한 기존 게시 파일을 참조합니다. 원본 및 720×465 게시본은 덮어쓰지 않습니다.
- 주문·결제·매출·재고 이력은 복사하지 않습니다. 재고는 추적 해제·수량 0으로 시작하고, 기준 매장의 일시적인 품절 상태와 할인 예약은 가져오지 않습니다. 개설한 매장에서 재고·할인 정책을 설정할 수 있습니다.
- 개설과 기본 구성 복사·점주 초대 등록은 하나의 DB 작업으로 처리합니다. 실패하면 전체를 취소하고 같은 요청의 재전송은 매장을 중복 생성하지 않습니다.
- 개설 후 **계정 관리**에서 대기 중인 점주의 **가입 안내 복사**를 누르고 직접 전달합니다. 초대 메일은 자동 발송되지 않습니다. 초대는 7일간 유효합니다.
- 점주는 안내 주소에서 초대된 이메일로 가입(비밀번호 6자 이상) → 이메일 인증 → 로그인합니다. 이미 같은 Firebase 계정이 있다면 로그인하면 됩니다. 점주에게는 해당 매장의 주문·메뉴·분류·매출·재고·광고·할인·계정 관리 기능이 모두 제공됩니다.
- 본사는 가맹점 목록에서 **매장 운영 관리**, **점주·구성원 관리**, **이 매장 키오스크 열기**를 이용합니다. 점주에게 본사 관리나 다른 가맹점 접근 권한은 주지 않습니다. 직원 역할은 주문 확인·조리만 필요한 경우 별도로 선택합니다. 구성원 초대의 기본 선택은 점주로 변경했습니다.
- 각 매장은 개설 당시 구성으로 시작한 뒤 독립적으로 운영합니다. 이후 본사 메뉴 변경을 기존 가맹점에 자동 덮어쓰는 기능은 포함하지 않습니다. 모든 매장은 같은 화면 코드를 사용하므로 시스템 기능 개선은 함께 적용됩니다.

실제 점주 이메일과 매장 이름을 임의로 만들어 운영 서버에 등록하지 않았습니다. 검사는 격리된 임시 매장으로 수행하며, 기존 매장과 점주 계정은 보존합니다. [검증 결과](tests/v1.9-validation.md)

## v1.8 — 점주 계정·이메일 복구·매장별 권한

공개 관리자 화면은 Firebase 이메일/비밀번호 계정을 사용합니다. Google 로그인은 필요하지 않습니다. 기존 메뉴·사진·주문은 매장 1에 그대로 연결되며, 매장별 메뉴·분류·광고·할인·주문·재고·매출과 호출 번호를 분리합니다. v1.8에서는 빈 메뉴로 개설했으나 v1.9부터 본사 관리의 기본 구성 복사를 사용합니다.

### 최초 점주 연결

1. 관리자 화면에서 **기존 관리자 암호로 로그인 → 계정 관리**로 이동합니다.
2. 사전에 지정한 최초 점주 이메일과 새 비밀번호(6자 이상)를 입력하고 **계정 가입·인증메일 받기**를 누릅니다. 이미 가입했다면 **인증메일 다시 받기**를 이용합니다.
3. 메일의 링크를 확인하고 돌아와 비밀번호를 다시 입력한 뒤 **인증한 계정으로 매장 연결**을 누릅니다.
4. 기존 데이터와 매장 1을 유지한 채 해당 계정에 최초 본사 관리자/점주 권한을 연결합니다. 이때부터 공용 관리자 암호·복구 코드와 기존 공용 세션은 사용할 수 없습니다. 이후에는 이메일로 로그인합니다.

비밀번호를 잊었다면 로그인 화면의 **비밀번호를 잊으셨나요?**에서 재설정 메일을 요청합니다. Firebase의 메일 링크에서 직접 변경합니다. 암호와 인증 토큰을 Git이나 보고서에 기록하지 않습니다.

### 매장·구성원 관리

- 본사 관리자: v1.9부터 **본사 관리 → 가맹점 개설 · 점주 초대**를 이용합니다. 기존 매장에 구성원을 추가하려면 해당 매장의 **계정 관리 → 이 매장에 구성원 초대**를 이용합니다.
- 점주: 자기 매장의 메뉴·주문·취소·매출·재고·광고·할인·구성원 관리. 다른 매장 주소나 ID를 입력해도 서버가 접근을 차단합니다.
- 직원: 자기 매장의 주문 조회와 조리 상태 변경만 가능합니다. 직권취소나 메뉴·매출·계정 관리는 허용하지 않습니다.
- 초대는 이메일과 권한을 7일간 등록하는 방식이며 **초대 메일은 자동 발송하지 않습니다**. 관리자 화면 주소와 가입 이메일을 구성원에게 안내합니다. 구성원이 가입·메일 인증 후 로그인하면 해당 매장에 연결됩니다.
- 구성원의 권한·사용 여부를 변경할 수 있으며 마지막 활성 점주는 해제할 수 없습니다. 비활성화는 다음 서버 요청부터 적용됩니다.
- 고객 화면은 `?store=매장번호`로 구분합니다. 관리자 상단 **이 매장 고객 화면**을 이용합니다. 장바구니와 고객 세션도 매장별로 구분합니다.

### 연결 설정과 검증 범위

Firebase Authentication에서 이메일/비밀번호를 켜고, 설정의 승인된 도메인에 Pages 호스트를 등록합니다. Firebase Hosting, Google 로그인, 서비스 계정 비공개 키는 이번 연결에 필요하지 않습니다. 서버 런타임의 `FIREBASE_PROJECT_ID`, `FIREBASE_WEB_API_KEY`, `KIOSK_OWNER_EMAIL`을 설정합니다. 마지막 값은 최초 연결에만 사용하며 Git에 저장하지 않습니다. 웹 API 키는 클라이언트 설정으로 전달되지만 관리자 권한은 Firebase 검증과 서버의 매장 구성원 조회로 결정합니다.

클라우드 서버는 Firebase REST의 토큰 조회를 통해 서명 검증된 사용자, 메일 인증, 만료·계정 정지·토큰 폐기 여부를 확인합니다. 브라우저는 비밀번호를 저장하지 않으며 세션 저장소의 로그인 토큰을 사용합니다. 브라우저의 매장 번호만으로 권한을 주지 않습니다.

Python 로컬 실행은 기존 **단일 매장 호환 모드**입니다. v1.8 다중 매장과 Firebase 연결은 공개 클라우드/API 구현에 해당합니다. 최초 점주 연결은 2026-11-27 사용자 완료 회신과 서버의 공용 로그인 종료로 확인했습니다. 실제 비밀번호 복구는 미실행이며, 자동 검사의 Firebase 응답은 임시 제공자로 대체합니다. 운영 PG·환불·푸시는 이번 버전에 포함하지 않습니다. [검증 결과](tests/v1.8-validation.md)

공식 참고: [Firebase Auth REST](https://firebase.google.com/docs/reference/rest/auth), [계정 및 비밀번호 관리](https://firebase.google.com/docs/auth/web/manage-users).

## v1.7 — 시간대 할인·새 메뉴

### v1.7.3 — 광고 조작 아이콘 하단 중앙 배치 (2026-11-27)

첫 화면은 **첫 화면 소식 → 우선 광고 → 최근 등록 메뉴부터 자동 소개 → 일반 광고** 순으로 반복합니다. 사진과 설명이 함께 옆으로 넘어가며 한 화면을 **10초** 동안 표시합니다. 광고 사진 하단 중앙의 작은 반투명 동그라미 버튼으로 이전·다음·일시 정지/재생을 조작합니다. 보이는 원의 지름은 44px에서 5.5px(1/8)로 줄였고, 버튼 중심 간격은 52px에서 24px로 줄였습니다. 각 버튼 입력 영역은 24×24px이며 서로 겹치지 않습니다. 긴 문구와 페이지 숫자는 고객 화면에 표시하지 않습니다. 직접 넘기거나 재생을 다시 시작하면 해당 화면부터 10초를 새로 셉니다. 다른 탭을 보거나 주문 화면에 들어가면 자동 넘김을 진행하지 않으며, 돌아오면 10초부터 시작합니다. 동작 줄이기를 사용하는 기기는 자동 재생을 끄고 슬라이드 애니메이션 없이 시작합니다.

기본 자동 소개는 **사진이 있고 현재 판매 가능한 메뉴**를 최신 등록순으로 표시합니다. 메뉴의 사진·이름·설명을 그대로 읽어 사용하므로 별도 광고 등록이 필요 없습니다. 메뉴 순서 변경이나 이름·가격 수정은 등록 순서를 바꾸지 않습니다. 메뉴 신규 등록·품절·사진 변경은 첫 화면의 약 15초 조회에 반영합니다. 현재 소개 중인 메뉴가 품절되면 첫 화면부터 다시 시작합니다.

관리자가 자동 소개보다 광고를 우선하려면 **광고 관리 → 광고 등록/수정 → 노출 위치 → 메뉴 소개보다 먼저 노출 → 광고 저장**을 선택합니다. 기본값인 **일반 광고**는 자동 메뉴 소개 뒤에 나옵니다. **첫 화면 소식**은 한 개만 지정할 수 있으며 현재 `새롭게 만나는 메뉴` 광고를 그대로 유지합니다. 같은 노출 위치의 광고끼리는 관리자가 정한 목록 순서로 표시합니다. 숨김 광고는 어느 위치에서도 나오지 않습니다.

기존 메뉴·사진·주문 및 광고 원본은 수정하지 않고, 자동 소개는 화면을 만들 때 계산합니다. 기존 `v1.7` 및 `v1.7-ad-slides` 태그를 보존하고 이후 `v1.7.1`, `v1.7.2`, `v1.7.3` 화면 보완도 별도 태그로 기록합니다.

관리자 **할인 관리 → + 할인 예약**에서 이름, 할인 방식, 요일, 시간, 선택 날짜, 대상 메뉴를 지정하고 **할인 저장**을 누릅니다. **할인율(1~99%) / 할인 판매가(원)** 두 방식과 가격 미리보기를 제공합니다. 목록에서 수정·켜기/끄기·삭제할 수 있으며 최대 30개를 예약합니다. 공개 매장에 임의의 활성 할인은 등록하지 않습니다.

- 한국 시간 기준으로 시작 시각부터 적용하고 종료 시각에는 끝납니다. 전체 하루는 `00:00~24:00`, `22:00~02:00`처럼 자정을 넘기면 시작한 날의 요일·기간을 기준으로 다음 날 종료합니다. 날짜를 비우면 반복 예약합니다.
- 메뉴 기본 가격만 할인하며 추가 옵션과 세부 선택 추가금은 유지합니다. 여러 예약이 겹치면 가장 낮은 가격 하나만 적용하고 중복 차감하지 않습니다. 할인율 결과는 원 단위로 내림합니다.
- 고객은 정상가·할인가·할인명·남은 시간을 확인합니다. 메뉴 목록은 약 15초마다 조회하며 팝업·결제 중에는 화면을 교체하지 않습니다. 장바구니에 담을 때 가격이 고정되는 것은 아니며, 주문 생성과 모의 결제 승인 시 서버가 다시 검사합니다. 달라졌다면 최신 금액의 장바구니로 돌아가 확인합니다.
- 주문 내역에는 당시 정상가·할인가·할인명을 남깁니다. 이후 예약을 삭제해도 승인 금액·매출·취소 기준은 바뀌지 않습니다. 관리자 메뉴 수정은 정상가를 편집합니다.
- 로컬 Toss 테스트는 결제창을 열기 전에 할인 금액을 확인하고 PG 결제 시도가 만들어진 뒤에는 해당 금액으로 인증·승인을 마칩니다. 공개 서버는 여전히 모의 결제이며 운영 PG, 재고 예약·환불 연동은 별도 작업입니다.

## v1.6 — 매출 분석·메뉴별 재고 관리

관리자 **매출 분석**에서 오늘·최근 7일·30일을 누르거나 시작일/종료일을 지정해 **조회**합니다. 최대 366일을 볼 수 있습니다. 순매출, 승인·취소 금액, 순판매 수량, 일별 내역, 인기 메뉴, 매장·포장 구분을 제공합니다. 현재 공개 매장의 금액은 **모의 결제 기록**입니다.

집계는 **한국 시간의 승인일 / 취소일**을 기준으로 합니다. 순매출은 해당 기간의 승인 금액에서 같은 기간에 발생한 취소 금액을 뺍니다. 어제 승인한 주문을 오늘 취소하면 오늘 취소 금액에 포함되어 순매출이 음수일 수도 있습니다. 인기 메뉴는 승인 수량순이며 취소 수량과 순판매를 따로 표시합니다. 미결제·실패 거래는 제외하고, 가격을 수정해도 주문 당시 옵션 포함 금액을 유지합니다. 세트·추가 옵션 금액과 판매는 대표 메뉴에 포함합니다. 순판매 수량의 취소 집계는 물리적 재고 복원 여부와 별개입니다.

관리자 **재고 관리 → 해당 메뉴 수량 수정 → 판매 가능 수량 관리 선택 → 수량·부족 기준·사유 입력 → 재고 저장**으로 시작합니다. 기존 메뉴는 **수량 관리 안 함**으로 보존되며 과거 주문을 소급 차감하지 않습니다. 수량은 완성 메뉴의 판매 가능 개수로, 재료나 세트에 들어간 다른 메뉴를 자동 차감하지 않습니다. 재료별 관리는 레시피와 옵션별 사용량 연결을 추가하는 다음 단계입니다.

- 장바구니에 담거나 결제에 실패하면 차감하지 않습니다. 모의 결제 승인과 동시에 주문 수량을 차감합니다.
- 0개가 되면 고객 메뉴가 흐려지고 품절로 표시됩니다. 열린 고객 화면은 약 15초 간격 또는 다시 활성화할 때 반영하고, 서버는 승인 시점의 최신 수량을 다시 확인합니다.
- 재고 부족 기준 이하에는 관리자 목록에 **재고 부족**을 표시합니다. **새로고침** 또는 탭 재진입으로 현재 수량을 확인합니다. 휴대폰 푸시 알림은 아닙니다.
- 입고·폐기·실사 조정은 변경 후 실제 수량과 사유를 입력합니다. 저장 전에 판매나 다른 수정이 발생하면 최신 수량을 불러오고 다시 입력하도록 안내합니다.
- **수량 관리 중지**는 수량 제한을 해제하며 기존 이력을 지우지 않습니다. **메뉴 관리**의 수동 품절은 별도이므로 보충해도 자동 해제하지 않습니다.
- **직권취소**에서 **이 주문에서 차감한 재고 복원**을 선택합니다. 조리 전 기본 선택, 조리 후 기본 해제입니다. 다시 팔 수 없는 음식은 복원하지 않습니다. 과거 미관리 주문은 복원할 재고가 없고, 중복 취소도 두 번 복원하지 않습니다.
- **최근 재고 변동**에서 최근 100건의 조정·판매·취소 수량, 사유, 주문번호를 확인합니다. 이전 기록은 DB에 보관됩니다.

현재 재고 자동 차감은 공개 매장의 모의 결제에 연결됩니다. 로컬 Toss 테스트는 재고 예약·실패 해제·환불 조정 연동 전까지 수량 관리 메뉴의 결제 시작을 차단합니다. 진행 중인 PG 거래가 있으면 해당 메뉴의 수량 관리를 켜지 못합니다. 실결제 운영 지원을 의미하지 않습니다. [v1.6 테스트 기록](tests/v1.6-validation.md)

## v1.5 — 광고 관리·매장/포장 첫 화면

고객은 첫 화면의 광고를 보고 **매장에서 먹기 / 포장하기** 중 하나를 선택해 주문을 시작합니다. 선택한 방식은 장바구니 상단, 결제 확인, 주문 완료, 관리자 주문 목록·상세에 표시합니다. 메뉴/장바구니의 **매장·포장 변경**으로 담은 메뉴를 유지하며 변경할 수 있습니다. 결제 완료 후 **처음으로**, 결제 전 **주문 전체 취소**는 이용 방식까지 초기화하고 첫 화면으로 돌아갑니다. **전체 비우기**는 이용 방식을 유지합니다.

관리자 **광고 관리 → + 광고 등록**에서 이미지·제목·설명·노출 여부를 입력합니다. 등록 후 **수정 / 숨기기·노출하기 / 삭제 / 앞으로·뒤로**를 사용할 수 있습니다. 삭제는 확인 후 적용하며 메뉴·사진·주문을 삭제하지 않습니다. 광고는 최대 10개이며, 제목은 40자, 설명은 120자까지 입력합니다. v1.7.1부터 전환 간격은 10초이며 광고 위에 이전·다음·일시 정지 아이콘 버튼을 제공합니다. 동작 줄이기를 설정한 브라우저는 자동 재생을 끈 상태로 시작합니다.

광고 이미지는 **1440×810px (16:9) JPG**로 게시합니다. JPG·PNG·WebP 10MB 이하 파일을 선택하면 비율을 유지해 자르고, 가로·세로 위치를 조절한 미리보기대로 저장합니다. 원본 파일과 기존 **720×465 메뉴 사진**은 변경하지 않습니다. 광고가 없거나 모두 숨겨져 있으면 기본 안내가 표시됩니다. 광고를 불러오지 못해도 메뉴 서버가 정상이라면 주문할 수 있습니다.

열린 첫 화면의 광고 변경은 약 15초 간격의 조회 또는 화면 재활성화 때 반영합니다. 과거 주문 및 구버전 화면에서 이용 방식 없이 생성한 주문은 **이용 방식 미기록**으로 표시하며 임의로 매장/포장을 지정하지 않습니다. [v1.5 테스트 절차·결과](tests/v1.5-validation.md)

## v1.4 — 분류·암호 관리

- **분류 관리 → + 분류 추가 → 분류 저장**: 이름 변경, 앞으로/뒤로 순서 변경, 빈 분류 삭제를 지원합니다. 1~20개, 이름 1~20자이며 중복 이름은 저장할 수 없습니다. 메뉴가 남은 분류는 먼저 메뉴 수정에서 다른 분류로 옮겨야 삭제됩니다. 고객 필터와 메뉴 등록·수정의 선택 목록에 같은 분류를 사용합니다.
- **암호 관리 → 현재 암호 / 새 암호 / 확인 → 암호 변경**: 새 암호는 12~128자입니다. 변경하면 모든 기기의 이전 로그인이 만료되고 기존 복구 코드도 무효가 됩니다. 변경된 암호는 DB에 솔트와 PBKDF2 해시로 보관하며 서버 재시작 후에도 유지됩니다.
- **암호 관리 → 복구 코드 발급 → 복구 코드 파일 저장**: 발급 직후에만 표시되는 일회용 코드를 별도로 보관합니다. 분실 시 로그인 화면의 **암호를 잊으셨나요?**에서 코드와 새 암호를 입력합니다. 재발급하면 이전 코드는 무효이며, 사용 후에는 새로 발급해야 합니다. 암호와 복구 코드를 모두 잃으면 운영자에게 서버 측 복구를 요청해야 합니다.
- 분류 수정은 기존 메뉴·사진·가격·옵션·주문 기록을 초기화하지 않습니다. 배포만으로 기존 관리자 암호도 바뀌지 않습니다. 암호 변경 및 복구 기능 시험은 임시 매장에서 수행했습니다.

앞으로 버전마다 [변경 기록](CHANGELOG.md), 해당 버전의 [테스트 절차·결과](tests/v1.6-validation.md), [버그 목록](BUGS.md)을 함께 갱신합니다. [배포 및 기록 절차](RELEASE_CHECKLIST.md)에 날짜·차수·예상/실제 결과·버그 연결 방법을 정리했습니다.

## v1.3 변경 사항

- **메뉴 관리 목록 → 품절 처리 / 판매 재개**로 바로 변경합니다. 사진·가격·옵션·메뉴 순서는 유지됩니다. 수정 화면 안의 판매 상태 설정도 계속 사용할 수 있습니다.
- 품절 메뉴를 고객 목록에서 숨기지 않고, 같은 자리에 사진을 흐리게 표시하면서 **품절** 배지를 붙입니다. 선택을 막고, 이미 담은 메뉴도 주문 생성과 결제 직전 서버에서 다시 검사합니다. 열린 고객 화면은 약 15초 간격의 조회 또는 다시 활성화할 때 반영합니다.
- **주문 현황 → 직권취소 → 사유 입력 → 직권취소 확정**으로 모의 결제된 주문을 취소합니다. 결제완료·조리중·준비완료까지 가능하고 수령완료는 제외합니다. 취소와 조리 시작이 겹치면 먼저 반영된 한 동작만 성공합니다.
- 취소한 주문은 **취소 내역**에 남으며 주문번호를 누르면 사유·시각·모의 취소 금액을 확인합니다. 해당 고객의 주문 완료 화면도 다음 조회에 취소 안내로 바뀝니다. 과거 주문 항목과 모의 승인 기록은 삭제하지 않습니다.

현재 직권취소는 **모의 결제 전용**입니다. PG 결제 주문은 환불 연동 없이 취소 완료로 바꾸지 않습니다. 기존 결제 전 고객 취소도 유지합니다. [v1.3 테스트 절차·결과](tests/v1.3-validation.md) · [버전별 변경 기록](CHANGELOG.md)

## v1.2 변경 사항

- 관리자 **메뉴 관리 → 앞으로/뒤로 → 순서 저장**으로 전체 메뉴와 분류별 노출 순서를 바꿉니다. 품절 메뉴도 순서를 유지하고, 새 메뉴는 마지막에 추가됩니다. 다른 관리자가 먼저 순서를 저장하거나 메뉴를 추가했다면 최신 목록에서 다시 정렬하도록 안내합니다.
- 주문 처리 중에는 해당 주문의 버튼만 잠깁니다. 다른 주문은 계속 조작할 수 있고, 자동 조회는 변경된 주문만 갱신합니다.
- 고객은 **전체 비우기** 또는 **주문 전체 취소**를 확인 후 실행할 수 있습니다. **메뉴 선택으로 돌아가기**는 장바구니를 유지합니다. 결제가 진행 중이거나 완료된 주문은 이 기능으로 취소하지 않습니다.
- 사이드 분류에서 설명 길이가 다른 메뉴끼리 나란히 놓여도 사진은 카드 위쪽에서 시작합니다. 게시용 사진은 720×465로 통일하고 목록에서는 원래 비율로 표시합니다. 사진 주변 테두리와 별도의 여백을 없앴습니다. 팝업의 높이 170px 표시는 유지합니다.

v1.2 시점의 취소는 결제 전 주문에만 적용됩니다. 관리자 직권취소는 v1.3, 자유로운 분류 관리는 v1.4, 메뉴별 재고·매출 분석은 v1.6에서 추가했습니다. 실제 운영 PG 결제·환불·재료별 재고는 후속 범위입니다.

고객은 휴대폰에서 바로 메뉴를 담고 모의 결제를 할 수 있습니다. 관리자는 다른 기기에서 로그인해 **주문 현황 → 새로고침**을 누르면 같은 주문번호와 옵션을 확인할 수 있습니다. 주문 목록은 열어 두면 약 8초 간격으로 갱신됩니다. 공개 매장은 공용 서버의 D1 데이터베이스를 사용하므로 개발 PC가 꺼져 있어도 이용할 수 있습니다. 결제는 과제 시연용 모의 카드 승인과 거절을 지원합니다.

공개 매장의 관리자 암호는 운영자에게 별도로 전달됩니다. 암호 원문은 저장소와 배포 파일에 포함하지 않습니다. 공개 매장의 주문 및 가격 설정은 아래의 로컬 SQLite 시연과 별도로 관리합니다.

## 매장에서 메뉴 등록하기

관리자 로그인 후 **메뉴 관리 → + 메뉴 등록**에서 메뉴명, 설명, 분류(분류 관리에서 설정), 가격, 판매 상태를 입력합니다. 치즈·소스처럼 동시에 담을 수 있는 항목은 **+ 옵션 추가**로 만듭니다. 음료처럼 한 가지를 골라야 하는 항목은 **+ 선택 그룹 추가**로 만들고 필수 여부를 설정합니다. 체크형 세트에는 **이 추가 옵션에 하위 그룹 추가**로 음료 질문을 연결합니다. 선택지 아래의 **이 선택지에 하위 그룹 추가**로 원하는 경우에만 다음 질문을 표시할 수 있습니다. 사진은 JPG·PNG·WebP 파일을 선택하면 **720×465 JPG**로 변환됩니다. 비율을 유지해 채우고 넘치는 가장자리를 자르므로 가로·세로 위치를 조절해 미리보기를 확인한 뒤 저장하세요. 사진을 생략하면 분류별 기본 그림을 사용합니다. [게시용 사진과 제작 기준](assets/menu/published/README.md)

**메뉴 등록하기**를 누르면 판매 중인 메뉴가 고객 목록에 표시됩니다. 이미 열려 있는 메뉴 목록은 약 15초마다 갱신됩니다. **수정**으로 사진·가격·옵션을 바꾸거나 품절 처리할 수 있습니다. 결제된 주문의 메뉴명과 옵션 금액은 구매 시점의 값으로 보관합니다.

## 로컬 실행

Python 3.10 이상에서 동작합니다. 로컬 모드는 Python 표준 라이브러리와 SQLite를 사용하므로 별도로 설치할 패키지가 없습니다.

```powershell
git clone https://github.com/9ardenx/burger-kiosk.git
cd burger-kiosk
python app.py
```

이미 소스가 있는 경우 그 폴더에서 `python app.py`만 실행하세요. [고객 키오스크](http://127.0.0.1:8000/)와 [관리자 화면](http://127.0.0.1:8000/admin)을 서로 다른 탭에서 열 수 있습니다. 최초 관리자 암호는 첫 실행 때 생성되는 `data/admin-code.txt`에서 확인합니다. 화면에서 변경한 뒤에는 DB에 저장된 새 암호가 적용되고 이 파일은 갱신하지 않습니다. 종료는 실행한 터미널에서 Ctrl+C를 누릅니다.

Windows에서 `python` 명령을 찾지 못하면 `py -3 app.py`를 사용하세요. 포트를 바꾸려면 `python app.py --port 8010`을 실행합니다. 개인 PC에서 시연할 수 있도록 루프백 주소에 바인딩합니다.

## 3분 시연

1. 키오스크 첫 화면에서 **매장에서 먹기** 또는 **포장하기**를 누른 뒤 **클래식버거**와 **치즈 추가**를 선택해 담습니다. 장바구니에서 수량을 2개로 바꾸면 합계가 12,000원입니다.
2. **주문 확인**에서 모의 승인 결과를 **승인 거절**로 선택하고 결제합니다. 실패 화면에서 **승인 성공 → 다시 결제**를 누르면 같은 주문에 새 결제 시도가 기록되고 주문번호가 발급됩니다.
3. 관리자 **주문 현황**에서 새로고침하고 주문번호를 눌러 옵션을 확인합니다. **조리 시작 → 준비 완료 → 수령 완료** 순서로 처리합니다. 완료된 주문은 **수령 완료** 필터에서 확인합니다.
4. 가격 변경을 시험하려면 고객 장바구니에 먼저 담고 관리자 **메뉴 관리**에서 가격을 바꿉니다. 결제 직전 변경된 가격을 안내합니다. 같은 방법으로 품절을 설정하면 결제가 차단됩니다. 이미 결제가 끝난 주문은 당시 단가를 유지합니다.

탄산음료에서는 음료 종류를 먼저 고릅니다. 콜라와 사이다는 일반·제로를 한 번 더 고르고, 오렌지 탄산은 바로 담을 수 있습니다. 각 선택지의 추가 금액을 합산하며, 다른 맛으로 바꾸면 이전 가지의 하위 선택을 지웁니다. 장바구니에서 **옵션 변경**으로 구성을 다시 고를 수 있습니다. 주문이 생성되면 당시의 그룹명·선택지·추가 금액을 보관합니다.

## 결제 모드

기본값 `demo`는 외부 통신 없이 모의 카드 승인과 거절을 재현합니다. 주문·결제 기록은 두 모드 모두 SQLite에 저장됩니다. 실제 PG 테스트 결제창을 사용하려면 토스페이먼츠 개발자센터에서 발급한 **API 개별 연동 테스트 키**를 같은 PowerShell 창에 설정한 뒤 시작합니다.

```powershell
$env:PAYMENT_MODE = "toss"
$env:TOSS_CLIENT_KEY = "<본인의 test_ck_ 키>"
$env:TOSS_SECRET_KEY = "<본인의 test_sk_ 키>"
python app.py
```

브라우저는 카드 결제창에서 인증하고, 서버는 저장된 주문 금액을 확인한 뒤 승인을 요청합니다. 중복 요청에는 같은 결제 시도 식별자를 사용합니다. 통신이 끊기면 **결과 다시 확인**으로 기존 거래를 확인할 수 있습니다. 기본 모드로 돌아가려면 `$env:PAYMENT_MODE = "demo"`로 바꾸고 서버를 재시작합니다. [결제창 연동 가이드](https://docs.tosspayments.com/guides/v2/payment-window/integration) · [승인 및 조회 API](https://docs.tosspayments.com/reference)

## 구조와 데이터

| 파일 | 담당 기능 |
| --- | --- |
| `app.py` | 서버 실행, DB 초기화, 관리자 암호 설정 |
| `docs/` | 고객·관리자 화면과 정적 자산. Pages에서는 공용 API, 로컬에서는 Python API에 연결 |
| `cloud/api.mjs`, `cloud/schema.ts` | 공개 매장의 주문·결제·관리자 API와 DB 스키마 |
| `kiosk/http.py` | 화면 및 API 라우팅, 관리자 세션 |
| `kiosk/orders.py` | 금액 재검증, 주문 시점의 단가·옵션 보존, 주문 상태 전이 |
| `kiosk/payments.py` | 결제 시도 이력, 모의 승인, 테스트 PG 연동과 결과 대조 |
| `kiosk/store.py`, `kiosk/schema.sql` | 메뉴·옵션·주문·주문 항목·선택 옵션·결제 저장 |

주문 상태는 `PENDING_PAYMENT → PAID → PREPARING → READY → COMPLETED`입니다. 결제 거절은 해당 시도만 `FAILED`로 기록하고 주문은 결제대기에 둡니다. 관리자 화면은 결제완료부터 주문을 표시합니다.

결제 전 취소는 `orders.cancelled_at`에 기록하며 API에서 `CANCELLED`로 표시합니다. 기존 주문 상태 제약과 과거 기록을 보존하기 위한 별도 필드입니다. 취소 기록이 있으면 결제 시도를 차단하고, 승인 여부가 미확정인 결제는 취소하지 않습니다. 메뉴 노출 순서는 `menu_display_order`에 별도로 보관하므로 순서 저장이 상품 가격·옵션 버전을 바꾸지 않습니다.

데이터베이스는 기본적으로 `data/kiosk.sqlite3`에 생성됩니다. 별도의 시연 데이터를 사용하려면 `python app.py --data-dir 다른폴더`로 실행하세요. 최초 관리자 암호를 지정하려면 시작 전에 `KIOSK_ADMIN_PASSWORD` 환경 변수를 설정합니다. 이미 화면에서 변경한 암호가 있으면 DB의 변경된 암호가 우선합니다.

## 테스트

```powershell
python -m unittest discover -s tests -v
```

테스트는 임시 DB에서 동시 결제, 재시도, 주문번호 중복 방지, 금액 보존, 품절 및 조리 상태 변경을 검증합니다. PG 응답의 불확실성과 승인 조회 재개는 테스트 대역으로 점검합니다. 외부 PG 결제창은 별도의 테스트 키와 네트워크 연결이 필요합니다.

공개 Worker API는 Node.js 24 이상에서 `node --test tests/cloud_v12.test.mjs`로 검사합니다. 실제 API 처리기와 SQL을 메모리 SQLite 어댑터에서 실행합니다.

사진 규격과 화면 표시는 `node tests/browser_photos.cjs`로 검사합니다. Playwright와 Chrome이 필요하며, 격리된 응답으로 사진 변환·관리자 미리보기와 저장 일치·6가지 화면 너비·100/125/150% 배율을 검증합니다. 실제 매장에는 쓰지 않습니다. [사진 규격 검증 기록](tests/photo-standard-validation.md)

브라우저 검사는 Playwright와 Chrome이 있는 환경에서 `node tests/browser_v12.cjs`, `node tests/browser_v13.cjs`, `node tests/browser_v14.cjs`, `node tests/browser_v15.cjs`로 실행합니다. Python을 사용해 별도 임시 DB와 서버를 자동으로 만들고, 종료 시 해당 서버를 중지합니다. 필요하면 `PYTHON`, `CHROME_PATH`를 지정하세요. 기존 매장 데이터는 사용하지 않습니다. 테스트 절차·예상 결과·실제 결과와 버그 연결은 [v1.2 검증 기록](tests/v1.2-validation.md)에 정리했습니다.
